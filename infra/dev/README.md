# Local Storj network for development and testing

Everything in this folder runs a **private Storj network on your machine** so
the MCP server can be exercised end to end without an account, credentials or
traffic to the real Storj network. It is built on
[storj-up](https://github.com/storj/up), the tool Storj itself uses for
development and CI.

What runs: one satellite (API + console), five storage nodes, Postgres, TiDB
and Redis. storj-up generates ten nodes; `slim.mjs` trims it to five and the
satellite is configured with erasure coding 1/2/3/4 so four nodes suffice. Images come from `ghcr.io/storj/up` and are multi-arch, so it runs
natively on Apple Silicon and on x86.

## Quick start

```bash
npm run docker:build          # once: build the MCP image (infra/Dockerfile)
npm run dev:storj up          # start the network and mint credentials
npm run test:e2e              # full tool lifecycle against the local network
npm run dev:storj down        # stop and delete all local data
```

`up` waits for the satellite, then runs `storj-up credentials` **inside** the
satellite container and writes an access grant to `infra/dev/.env`
(git-ignored). The grant points at `satellite-api:7777`, which is the address
the MCP container can reach on the compose network.

## Using it from an MCP client

Point the client at the MCP container joined to the local network:

```json
{
  "mcpServers": {
    "storj-local": {
      "command": "/absolute/path/to/storj-uplink-mcp/infra/dev/storj-local.sh",
      "args": ["mcp"]
    }
  }
}
```

`infra/dev/exchange/` is mounted at `/data` in the container, so
`upload_file` / `download_file` prompts should use `/data/...` paths.

The satellite web console is at <http://localhost:10000>
(user `test@storj.io`, password `password`, created by `storj-up credentials`).

## What the end-to-end test covers

`infra/dev/e2e.mjs` runs the **production image** over stdio and asserts:
create/stat bucket, `upload_text` with metadata, `list_objects` structured
output (recursive and prefix mode), `stat_object` metadata round-trip,
`peek_object_head` / `peek_object_tail` / `grep_object`, `download_text`,
`copy_object` + `move_object`, `bucket_usage`, `download_file` +
`upload_file` through the `/data` volume, `delete_objects` by glob,
`share_access`, and `delete_bucket --with_objects`. It creates a uniquely
named bucket and removes it, even on failure.

## Files

| File | Purpose |
|---|---|
| `docker-compose.yaml`, `tidb.toml`, `tidb-init.sql` | generated by `storj-up init db,minimal` + `slim.mjs`; regenerate with `storj-local.sh regenerate` |
| `slim.mjs` | trims the generated file to five storage nodes |
| `docker-compose.mcp.yml` | overlay adding the hardened MCP container to the same network |
| `storj-local.sh` | up / status / credentials / mcp / e2e / logs / down / regenerate |
| `e2e.mjs` | the end-to-end test |
| `.env` (git-ignored) | local access grant written by `up` |
| `exchange/` | host folder mounted at `/data` for the local-file tools |

## Footprint

Images to pull: `ghcr.io/storj/up/storj` (about 0.95 GB compressed, roughly
3 GB on disk), `pingcap/tidb` (1 GB on disk), `postgres` (0.7 GB), `redis`
(0.15 GB). Budget about 6 GB of free Docker disk for images plus data. On a
nearly full disk the pull stalls the Docker daemon, so check `docker system
df` first.

## Notes

- `storj-up` itself is only needed on the host to **regenerate** the compose
  file (`go install storj.io/storj-up@main`). Everyday use needs Docker only,
  because credentials are minted with the copy of `storj-up` bundled in the
  satellite image. Install from `@main`: the tagged releases still reference
  the retired `img.dev.storj.io` registry.
- Everything runs as compose project **`storj-up`**; `down` removes only
  that project's containers and volumes. It never touches other projects'
  volumes (self-hosted databases, other stacks). If you need to reclaim
  Docker disk space, prefer `docker image prune` / `docker builder prune`;
  avoid `docker volume prune` and `docker system prune --volumes`, which
  delete every volume not attached to a running container.
- Ports 4000, 5432, 7777, 10000 and 30000–30090 are published on localhost
  by the generated file. Nothing here is hardened; it is a development
  fixture, not a deployment.
- Storj's other option, `storj-sim` (plain binaries, no Docker), is not
  wired up here.
